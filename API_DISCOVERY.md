## Selected API

- Endpoint: `https://cdui-orchestrations.target.com/cdui_orchestrations/v1/pages/slp`
- Method: `GET`
- Auth: No account auth required. A modern browser fingerprint and desktop browser headers are required for stable access.
- Client: `impit` with browser emulation `chrome151` (browser-consistent TLS + HTTP/2 fingerprint; fingerprint headers are generated by impit and are not hand-overridden).
- Pagination: `offset` + `count` with metadata under `data_source_modules[].module_data.search_response.search_response.metadata`
- Required params verified: `key`, `platform`, `channel`, `sapphire_channel`, `page`, `sapphire_page`, `visitor_id`, `keyword`, `offset`, `count`, `store_id`, `scheduled_delivery_store_id`, `zip`, `state`, `include_data_source_modules`
- Fields available: product identifiers, title, brand, URLs, pricing, ratings, review summary, fulfillment, shipping availability, swatches, category IDs, image URLs, promotions, ornaments, and pagination metadata
- Field count: 30+ practical product fields with stable pagination metadata

## Why This API Won

- Returns rich JSON directly and paginates cleanly with `offset=24`, `48`, and beyond.
- Works reliably through `impit` browser emulation; every tested fingerprint returned clean product data.
- Exposes the same product objects the listing page renders, plus search metadata in one response.
- Keeps the actor fully HTTP-based without a real browser.

## Runtime Flow

1. Build the listing request from the supplied keyword/URL and store context.
2. Fetch the CDUI page with `impit` using browser emulation (no manual `user-agent`/`sec-ch-ua` overrides).
3. Parse products from `data_source_modules[].module_data.search_response.products`.
4. Parse pagination metadata from `data_source_modules[].module_data.search_response.search_response.metadata`.
5. Advance `offset` by the metadata `count` (default 24) and repeat until `results_wanted`, `max_pages`, or `total_results` is reached.

## Failure Diagnosis: HTTP 435

The previous `got-scraping` implementation intermittently received `HTTP 435` with a body whose top-level keys were `appId`, `blockScript`, `firstPartyEnabled`, `hostUrl`, `jsClientSrc`, `uuid`, `vid`. That is a HUMAN / PerimeterX bot-defense block page, not a Target application error. It is triggered per client/IP reputation and can appear after only one successful request on a residential exit IP.

Fixes applied:

- Switched the request client from `got-scraping` to `impit` browser emulation so the TLS/HTTP2 fingerprint and header order match a real browser, while removing hand-written and potentially contradictory `user-agent` / `sec-ch-ua` headers.
- Rotate the Apify proxy session for every request attempt (a fresh exit IP per request) instead of reusing one exit IP for the whole run.
- Bounded retries with backoff for `403`, `408`, `429`, `435`, and `5xx`, plus malformed JSON bodies. Permanent `4xx` responses are not retried.
- Every fetch and parse is wrapped so one bad page stops pagination gracefully instead of throwing an uncaught exception.

## Rejected / Fallback Candidates

### Legacy RedSky listing endpoint

- Endpoint: `https://redsky.target.com/redsky_aggregations/v1/web/plp_search_v2`
- Result: not usable for pagination.
- Rejection reason: Page 1 (`offset=0`) returns products, but `offset=24` and later return `{"errors":[{"message":"No product found with tcin ..."}]}` with HTTP 200 and no products. It also rejects `scheduled_delivery_store_id=3991` with `cannot be digital store`. It is not a reliable paginator and was removed as a fallback.

### Reviews endpoint (r2d2)

- Endpoint: `https://r2d2.target.com/ratings_reviews_api/v1/summary`
- Result: reachable and returns reviews, but out of scope for this actor.
- Note: the actor collects product data only and does not call this endpoint.

### Sapphire runtime endpoint

- Endpoint: `https://sapphire-api.target.com/sapphire/runtime/api/v1/raw/www.target.com/s`
- Result: removed. A random visitor id and a directly built page path are accepted by CDUI, so the extra bootstrap request only added a failure surface and latency.

## Live Validation Notes

- Direct `impit` probes confirmed the CDUI endpoint returned clean product data for `offset=0/24/144/216` with `chrome151`, `chrome142`, `chrome131`, `firefox144`, and `ios18`.
- `offset` 216 returned 24 products while earlier pages returned 29-30, confirming live pagination.
- A search that Target redirects (for example `womens tops`) returns a `redirect_url` with no product array and is handled as a clean stop, not an error.

## Observed Browser Request Headers

The successful CDUI request uses these header types:

- `Accept: application/json`
- `Referer`
- `User-Agent`
- `Sec-CH-UA`
- `Sec-CH-UA-Mobile`
- `Sec-CH-UA-Platform`

With `impit` these fingerprint headers are generated by the emulated browser. Only `accept`, `accept-language`, and `referer` are set explicitly; `referer` is the Target search page for the keyword/URL. Keep the browser value and any explicit header values consistent.

## Auto-Healing Guidance

- If the actor fails, read this file first.
- A `435` response is a bot-defense block: rotate the proxy session and retry with a bounded budget; do not treat it as target data.
- If CDUI stops returning products but returns `200`, log the response keys and check for a `redirect_url` before retrying.
- Do not reintroduce the RedSky listing endpoint as a paginator; it is broken beyond `offset=0`.
